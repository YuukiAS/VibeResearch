# VibeResearch 0.7.0 Decision-To-Execution Architecture Plan

This plan upgrades VibeResearch from a lifecycle/state-machine scaffold into a
generic decision-to-execution framework. The implementation must stay project
agnostic: downstream repositories should attach their own adapter/config, while
the main framework only enforces structured decisions, executable plans, trusted
metrics, and visible block states.

Do not modify downstream project repositories while implementing this plan.
Before every commit, update `CHANGELOG.md`.

## Summary

VibeResearch 0.6.0 can plan, review, generate, submit, collect, reflect, revise,
render dashboards, and run local/Slurm backends. The exposed failure mode is
that those lifecycle steps can keep advancing while no real scientific
experiment has happened:

- repeated evidence-only cycles;
- placeholder commands submitted through local or Slurm backend;
- missing metrics silently becoming `primary_metric=0.0`;
- untrusted results appearing in leaderboard/history;
- offline fallback repeating `collect_more_metrics` with no promotion;
- dashboard/timeline showing movement without trusted evidence.

0.7.0 must make this impossible by separating:

- lifecycle execution state: command reviewed, dry-run passed, submitted,
  finished, collected;
- research decision state: promote, stop, ask user, request deep research,
  launch gate, or block;
- scientific evidence trust state: schema-valid, trusted, untrusted, blocked.

## Core Principles

- Agent research judgment remains outside deterministic framework code.
- Framework code does not invent project-specific scientific routes.
- Every research judgment must become structured, executable, and auditable
  before it can affect scheduling.
- Project adapters expose capabilities and validation rules, not hidden
  research strategy.
- Offline fallback means safe block, missing-information marker, or lightweight
  audit only. It must not create fake experiments or fake promotion.
- Placeholder commands, missing metrics, and missing adapters are explicit block
  states, not successful experiments.

## Phase 1: Structured Research Decision Contract

### Data Model

Add a structured decision model in a new module such as
`vibe_research/decisions.py`.

Required fields:

- `decision_id`
- `target_type`: `run` or `cycle`
- `target_id`
- `decision_type`
- `rationale`
- `selected_direction`
- `required_action`
- `expected_evidence`
- `resource_intent`
- `metrics_requirements`
- `baseline_comparison_target`
- `blocking_questions`
- `confidence`
- `provenance`
- `created_at`

Required `decision_type` enum:

- `collect_more_metrics`
- `launch_gpu_gate`
- `promote_to_baseline_compare`
- `stop_direction`
- `request_deep_research`
- `ask_user`
- `blocked_missing_decision`
- `blocked_missing_adapter`
- `blocked_missing_resource_plan`
- `blocked_repeating_evidence`

Do not fall back to free-form Markdown decisions for scheduling decisions.
Markdown plans can explain reasoning, but scheduling must use the structured
decision JSON.

### Decision Files

Write decisions to:

- run-level: `.vibe/runs/<run_id>/decision.json`;
- cycle-level: `.vibe/cycles/<cycle_id>/cycle_decision.json`;
- optional audit stream: `.vibe/state/decisions.jsonl`.

Each `revise-plan` must leave either a valid run decision or a block decision.
Each `revise-cycle` must leave either a valid cycle decision or a block
decision.

### CLI

Add:

- `vibe validate-decision <target_id>`;
- `vibe decision show <target_id>` or equivalent;
- `vibe decision write-block <target_id> --reason ...` if useful for tests and
  operator recovery.

Validation errors must be user-readable and must include the target id.

## Phase 2: Project Adapter Interface

### Adapter Scope

Add a generic adapter layer in a new module or package such as
`vibe_research/adapters/`.

The adapter describes project capabilities:

- available task types;
- command templates or entrypoint capabilities;
- dry-run policy;
- resource defaults;
- expected output paths;
- metrics schema;
- baseline target requirements;
- trusted artifact pattern;
- safe offline audit capability.

The adapter must not make hidden research choices. It only says what the
project can execute and how results can be trusted.

### Default Adapters

Implement:

- `NoopAdapter`: default for projects with no adapter; it cannot compile
  scientific experiments and returns `blocked_missing_adapter`.
- `ConfigAdapter`: reads generic adapter/capability declarations from
  `.vibe/config.yaml` or a dedicated `.vibe/adapter.yaml`.
- `ToyAdapter`: test-only or docs-only minimal example with generic commands
  and generic metrics; it must not be project-specific.

No downstream project names, metric names, paths, scripts, or Slurm settings
may be hardcoded in the main framework.

### Config Shape

Extend config defaults with an adapter section similar to:

```yaml
adapter:
  kind: noop
  config_path: .vibe/adapter.yaml
  require_for_experiments: true
```

The exact YAML structure can be refined during implementation, but it must be
schema-validated and documented.

## Phase 3: Decision-To-Execution Compiler

### Compiler Behavior

Add a promotion planner/compiler in a module such as
`vibe_research/promotion.py`.

Inputs:

- structured decision JSON;
- current adapter capabilities;
- current state and run metadata;
- current resource plan, if present;
- leaderboard/trusted metric summary;
- scheduler budget.

Outputs:

- executable `resource_plan.yaml`; or
- explicit block state with block reason and missing requirements.

The compiler must never silently generate placeholder commands.

### Executable Resource Plan Requirements

Every compiled run spec must include:

- stable task key;
- `direction_id`;
- hypothesis or expected learning;
- non-placeholder `dryrun.command`;
- non-placeholder `entrypoint.command`;
- resources: GPU, CPU, memory, walltime, partition hints if applicable;
- expected output path;
- metrics file path;
- required metrics schema;
- trust rules;
- baseline comparison target when decision requires baseline comparison;
- dependency and cancellation metadata.

If any required field is missing, write a block decision/state instead of a
run spec.

### Integration Points

- After `revise-plan`, write/validate run decision and update run state.
- After `revise-cycle`, write/validate cycle decision and run the compiler.
- `plan-cycle` may still create a Markdown portfolio plan, but run generation
  must use executable resource plans created or validated by the compiler.
- `generate-runs` must reject placeholder plans unless explicitly running a
  toy/mock adapter test path.
- `compute_next_action()` must check block states and structured decisions
  before continuing lifecycle actions.

### CLI

Add:

- `vibe compile-decision <cycle_id>`;
- `vibe validate-resource-plan <cycle_id>` or extend existing hard-rule
  validation.

Compiler failures must set:

- cycle or run status to `blocked`;
- `state.blocked_reason`;
- a timeline event with a specific block reason.

## Phase 4: Metrics Schema Enforcement and Trust Gating

### Collection Semantics

Modify `collect()` so command completion and scientific trust are distinct.

Allowed outcomes:

- command finished, metrics missing: untrusted or blocked;
- metrics present but schema-invalid: `failed_schema_validation`;
- metrics present and schema-valid but provenance incomplete: untrusted;
- metrics present, schema-valid, provenance-complete: trusted candidate;
- trusted candidate promoted only after required reflection/revision gates.

`--metric` may remain for manual/debug compatibility, but it must not create
trusted scientific evidence unless the run is explicitly configured as a
manual metric task with schema/provenance satisfied.

### Required Validation

For experiment-like runs, validate:

- metrics file exists;
- required metric keys exist;
- metric values have valid numeric/string/bool types according to schema;
- expected output path exists when required;
- baseline comparison target exists when required;
- manifest commands are non-placeholder;
- provenance requirements are satisfied.

Suggested new fields in `metrics.json`:

- `primary_metric`
- `metrics`
- `trusted`
- `trusted_candidate`
- `trust_status`
- `schema_status`
- `schema_errors`
- `missing_metrics`
- `block_reason`
- `evidence_level`
- `provenance`

### Leaderboard Rules

- Only trusted, schema-valid rows update `best.json`.
- Only trusted, schema-valid rows update `best_by_direction.json`.
- Keep untrusted/debug rows out of trusted leaderboard ranking.
- If untrusted rows remain in `history.jsonl`, dashboard must label them
  clearly as untrusted/debug and include the reason.

`primary_metric=0.0` from fallback/default/missing metrics must never be treated
as a real failed experiment or trusted result.

## Phase 5: Offline Fallback Safety

Modify offline fallback in `codex_adapter.py`.

New behavior:

- run/cycle revised-plan fallback writes a structured block decision;
- default block reason is missing structured decision, missing adapter, or
  missing resource plan;
- no fallback path may claim promotion or propose GPU/baseline experiments
  without adapter support;
- if a safe audit task exists in the adapter, fallback may compile only that
  audit task;
- offline artifacts should explain the block in Markdown for humans, while
  `decision.json` or `cycle_decision.json` controls scheduling.

Update artifact validation to require consistency between revised-plan Markdown
and structured decision files.

## Phase 6: Anti-Loop Detector

Add an anti-loop detector in a module such as `vibe_research/loop_guard.py`.

### Detection Signals

Use deterministic, dependency-light signatures:

- no new trusted metrics across N consecutive cycles;
- same decision type repeated, especially `collect_more_metrics`;
- repeated block/fallback provenance;
- repeated evidence-only run names;
- repeated run descriptions/hypotheses after normalization;
- resource plan empty, missing, or placeholder;
- no executable entrypoint;
- no metrics schema;
- repeated `primary_metric=0.0` from untrusted/default source.

Default threshold: 2 consecutive repeated cycles or runs, configurable in
`.vibe/config.yaml`.

### Block Behavior

When triggered:

- write structured decision with `blocked_repeating_evidence`;
- set cycle or project state to blocked;
- set `state.blocked_reason`;
- record timeline event `blocked_repeating_evidence`;
- show likely missing cause:
  - missing structured decision;
  - missing adapter;
  - missing resource plan;
  - missing real metrics;
  - missing user decision.

The detector should stop fake progress but not prevent normal multi-round
research when trusted evidence or a genuinely new executable plan appears.

## Phase 7: Dashboard, Timeline, and Status Visibility

Update renderers so users can distinguish lifecycle progress from scientific
evidence.

### Status and TODO

Show:

- lifecycle status;
- trust status;
- schema status;
- block reason;
- next structured decision action.

Blocked items should appear in the BLOCKED section, not as successful DONE
items.

### Leaderboard

Show trusted leaderboard separately from untrusted/debug collection history.
For each row, include:

- run id;
- direction;
- primary metric;
- trusted;
- trust status;
- schema status;
- block reason.

### Timeline

Add specific event types:

- `decision_written`;
- `decision_blocked`;
- `resource_plan_compiled`;
- `resource_plan_blocked`;
- `metrics_untrusted`;
- `metrics_schema_failed`;
- `trusted_evidence_recorded`;
- `blocked_repeating_evidence`.

Avoid emitting a generic `leaderboard_updated` event for untrusted metrics.

### Static Dashboard

Ensure the static site surfaces the same trust/block fields as Markdown mirrors.

## Phase 8: Backward Compatibility and Migration

Existing 0.6.0 projects must remain readable and diagnosable.

Migration behavior:

- if no adapter exists, block on experiment compilation with
  `blocked_missing_adapter`;
- if an existing resource plan has real commands and metrics schema, validate
  and allow it;
- if an existing resource plan has placeholder commands, block before queue;
- if old metrics history includes untrusted rows, keep the file but do not use
  those rows for trusted best selection;
- existing CLI commands should remain available unless a safety block is
  required.

Update config schema version and provide a lightweight migration path through
existing config migration helpers.

## Phase 10: Tests

Use pytest and temporary toy projects. Do not require Codex auth, network,
Slurm, GPU, or downstream project repositories.

### Decision Tests

- valid decision parses;
- invalid enum fails;
- missing required action fails for executable decisions;
- block decision accepts block reason;
- `vibe validate-decision` returns success/failure correctly.

### Adapter and Compiler Tests

- noop adapter returns `blocked_missing_adapter`;
- toy adapter valid decision compiles executable resource plan;
- missing entrypoint blocks with `blocked_missing_resource_plan`;
- placeholder command blocks;
- baseline compare without target blocks;
- compiled plan includes expected output, metrics path, schema, and trust rules.

### Metrics and Trust Tests

- missing metrics file creates untrusted result;
- missing required metric key creates schema failure;
- wrong metric type creates schema failure;
- placeholder command cannot become trusted evidence;
- untrusted run does not update `best.json`;
- trusted schema-valid run updates `best.json`;
- `primary_metric=0.0` from missing/default metrics is untrusted.

### Offline and Automation Tests

- offline revised-plan writes block decision;
- offline cycle-revised-plan writes block decision;
- `auto-cycle --offline` stops at explicit block without fake progress;
- repeated evidence-only cycles trigger `blocked_repeating_evidence`;
- repeated untrusted `primary=0.0` triggers anti-loop block;
- existing local and Slurm dry backend tests still pass with valid toy adapter
  or validated resource plan.

### Dashboard and Timeline Tests

- status includes trust and schema status;
- leaderboard excludes untrusted rows from best;
- timeline records block and schema failure events;
- TODO blocked section shows missing adapter/resource/metrics loop reason.

## Acceptance Criteria

- Lifecycle state and research decision state are distinct in code and UI.
- Every revise step produces a structured decision or explicit block.
- No real scheduling proceeds from placeholder commands.
- No experiment-like run becomes trusted without metrics file and schema
  validation.
- Missing metrics do not become trusted `primary_metric=0.0`.
- Offline fallback no longer generates fake progress.
- Repeated evidence-only cycles block with `blocked_repeating_evidence`.
- Dashboard/timeline show trusted, untrusted, blocked, and schema-failed states.
- README includes the 0.7.0 three-layer architecture and Mermaid diagram.
- Version reports `0.7.0`.
- Tests cover the core safety and regression behavior.
- Main framework contains no downstream-project-specific hardcoding.
